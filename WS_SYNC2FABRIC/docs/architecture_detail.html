Things the log shows

Three failures before the local copy worked

(1) The warehouse COPY command refused the SQL Server source ("doesn't support 'Source connector type' as 'SqlServer'"): fixed with enableStaging: true. (2) The gateway could not impersonate the Windows user: switched to a SQL login. (3) The connection still held another user name (fabric_local_user vs the login first created as fabric_local_reader): the login was renamed to match. Each failed run took 20 to 60 s.

One row costs a minute

The pipeline run took 61 s for a single row, against 0.03 s to read the same table over the Azure SQL path. The time is the pipeline, the gateway hop and staging, not the data. It matters if you ever schedule this.

18 token requests = about 18 s

Each Invoke-Fabric and Invoke-Sql asks az again, about 1 s each (one took 2 s). Caching a token per resource for the run would save roughly 15 s of the 104 s.

Entra admin is set every run

az sql server ad-admin create takes 17 s and repeats although the server already exists. Guarding it with ad-admin list would remove half of step 01.

Azure SQL vs warehouse latency

The select on Azure SQL took 0.03 s; each warehouse statement took 2 to 5 s, and the first one 4.8 s. That is typical for the warehouse endpoint and the reason a one-row load stays in a script.

Warehouse creation is asynchronous

The POST returns 202; the script polls the operation for about 21 s and then looks the warehouse up again. The operation URL pointed to a Switzerland North service host while the capacity is in West Europe: worth knowing if data residency matters.

Connection created, not used

The Fabric connection with fabric_reader passed its connection test, but nothing uses it yet: the Azure row is loaded by the script. It is kept for a future pipeline and removed by cleanup. The gateway connection conn-local-sql is different: it is created by hand and is not removed by cleanup.
